# 百度智能小程序 — 开放联盟型宿主：搜索流量分发模型参考

> 快照日期：2026-10-16 ｜ 来源：GitHub org `swan-team`（api.github.com 当日实测逐仓核对）、smartprogram.baidu.com 文档体系（模型知识互证）｜ 容器本体闭源，凡标 *UNCERTAIN* 者使用前必须复核

## ① 项目画像

**百度 App 内的小程序运行时（Swan）**，2018-07 上线，主打**搜索流量直连**（搜索结果卡片直接挂小程序，页面可被百度索引）与**开放联盟**（2018-11 起向爱奇艺/百度地图/ WiFi 万能钥匙等百度系及联盟宿主输出运行时，形成"宿主 App 开放接入"的联盟模型——`swan-team/host-app-guide`"开源宿主接入文档"即此产物）。治理同微信式封闭，且**开源投入已实质性终止**：org `swan-team` 全部 5 仓库当日实测——swan-docs（官方文档镜像）pushed **2020-04**、host-app-guide pushed **2019-09**、swan-example pushed **2018-12**、specs pushed **2019-11**、awesome-swan pushed 2020-03——**GitHub 面六年无活跃**，生态重心完全退回自有文档站与百度 App 客户端灰度。

## ② 架构与原理（与 OmniLet 相关部分）

1. **双线程同源流派**：逻辑层（Swan 核心，JS 引擎按端选择）与渲染层（系统 WebView）分离；语法与微信高度同构（`swan.*` API、view/scroll-view 组件族、Page/App 生命周期），官方提供微信迁移工具——**"联盟端≈微信方言"的最强证据链**。
2. **联盟输出架构**（对 OmniLet 最有价值的部分）：Swan 运行时以 SDK 形式嵌入多个宿主 App（爱奇艺/百度地图/WiFi 万能钥匙等），**宿主可自定义 API 面与视觉皮肤**（能力声明/组件开放度/API 白名单按宿主裁剪，host-app-guide 记录了文档形态）——这是"容器 SDK 卖给多个宿主"模式的**最早规模化实践，早于 FinClip 的商业化**。
3. **搜索分发协议**：小程序页面通过页面配置 + 结构化数据声明进入百度索引，搜索结果卡片直连小程序——**流量分发与运行时耦合**的独特设计，微信/支付宝均无。
4. **渲染栈**：系统 WebView 混合渲染为主，无公开自研 GPU 引擎证据。

## ③ 功能与特性

- **发布体系**：百度智能小程序平台审核 + 灰度；联盟宿主间分发靠协议而非统一审核（各宿主保留自己的准入门槛）。
- **沙箱与权限**：容器级沙箱 + API 白名单按宿主裁剪——同一小程序在不同联盟宿主内能力面可能不同（宿主定制点的运行时体现）。
- **自然语言/搜索工具链**：页面索引声明、结构化数据、小程序sitemap——面向搜索引擎的 SEO 式工具链，其他家没有。
- **工具链现状**：百度开发者工具（IDE）闭源；官方 GitHub 工具链全部停更（见 ①）。
- **生态位**：搜索/长尾信息类小程序（问卷、工具、本地服务），开发者生态收缩中。

## ④ 优缺点

**优点**：联盟模型先例——多宿主容器输出的架构与文档形态（按宿主裁剪能力面）已被规模化验证；搜索分发协议是与运行时耦合的独特流量模型；语法同构微信，编译器适配成本低；宿主定制面（API 白名单/皮肤）有现成文档范式。

**缺点/短板**：官方开源面 2019-2020 后全面停更，生态明显收缩；流量盘子依赖百度 App 单端，搜索分发红利未兑现为开发者繁荣；作为编译目标的商业优先级低——白皮书 §7 对比表未列百度端为独立发布端，OmniLet 路线图中按联盟族归并顺带覆盖。

## ⑤ 对 OmniLet 的可借鉴点（映射到模块）

1. **多宿主容器输出的架构先例**：Swan 联盟 = "同一运行时 + 按宿主裁剪 API 面/视觉"的最早规模化实践——OmniLet 容器 SDK 的宿主定制机制（能力声明/白名单/皮肤）可循此设计；host-app-guide 的文档结构（能力声明 + 组件开放度 + API 白名单）是宿主接入文档的现成模板（→ 容器 SDK/文档）。
2. **宿主能力裁剪的运行时机制**：同一小程序包在不同宿主能力面不同 → OmniLet 容器的权限集注入（architecture.md §③"沙箱创建(权限集注入)"）在设计上已覆盖此形态，Swan 是其被验证的先例——自有容器未来作为 SDK 输出给多宿主时直接沿用（→ 容器 SDK/沙箱）。
3. **"联盟族"编译收敛**：百度端语法与微信高度同构——编译引擎按方言差异表（API 前缀 `swan.*` + 少量组件差异）适配，验证"逐端适配→按族收敛"的省力路径（→ 编译引擎/条件编译；与 alipay-miniprogram.md ⑤.3 联盟收敛互为表里）。
4. **流量分发与运行时耦合**（反差价值）：搜索直连是百度独有的"容器即流量入口"设计——OmniLet 管理后台做"内容分发/检索"类增值能力时可参照其页面索引协议思路（→ 管理后台，远期）。
5. **签名校验的联盟协议化**：联盟宿主间分发靠协议约定——OmniLet 离线包签名校验（architecture.md 不变量⑤，fail-closed）在企业多宿主场景下需要等价的"宿主间信任协议"设计空间（→ 沙箱/离线包，远期）。

## ⑥ 不借鉴/规避点

1. **开源工具链断供路线**：GitHub 面六年无活跃 = 生态信心的慢性流失。OmniLet 编译器/工具链若开源，必须持续投入而非一次性展示（→ 产品定位）。
2. **单宿主依赖**：联盟分发随百度 App 的商业重心波动——OmniLet 的自有容器路线正是对这种平台依赖的解药，不可反向滑回"依赖单一外部宿主"（→ 产品定位）。
3. **作为编译目标的优先级**：二阶段落地清单中百度端不单列，随联盟族适配顺带覆盖；不为它单独设计条件编译分支（→ 编译引擎/路线图）。
