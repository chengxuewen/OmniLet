# 支付宝小程序 — 第二目标平台：开放能力差异 + 渲染栈

> 快照日期：2026-10-16 ｜ 来源：GitHub org `ant-mini-program` / `remaxjs` / `ant-move` / `antvis`（api.github.com 当日实测）、open.alipay.com 开放能力体系（模型知识互证）｜ 容器本体闭源，凡标 *UNCERTAIN* 者使用前必须复核

## ① 项目画像

**蚂蚁集团超 App（支付宝）内的小程序运行时**，2018-09 公测，是微信之后第二个成体系的小程序宿主，也是**开放联盟（Alchemy 开放联盟）的事实输出方**——百度/字节/360/iQOO 等联盟成员的运行时与支付宝同源度高，"手机 App 开放接入小程序运行时"的联盟模式由支付宝系率先规模化。与微信的关键差异：**强账号/支付/信用/生活服务开放能力**（`my.*` API 面向商业服务闭环），弱社交传播。治理同微信式封闭：审核发布走支付宝开放平台，容器引擎与开发者 IDE 全闭源；开源面为工具链与组件库，且维护强度明显弱于微信（org `ant-mini-program` 当日实测：mini-antui 450★ 官方宣布停止维护转向 mini-ali-ui、api-typings 26★ pushed 2024-11、mini-types 42★ 冻结 2022）。第三方生态承担框架层：Remax 4548★（真实 React 写小程序，**pushed 2024-03 后停滞**）、Antmove 1327★（微信→支付宝转换器，停于 2023-11）——**支付宝端框架生态在收缩**。

## ② 架构与原理（与 OmniLet 相关部分）

1. **双线程同源流派**：逻辑层（JSCore/V8，无 DOM/BOM）与渲染层（系统 WebView）分离，AXML/ACSS 模板 + `setData` 序列化 IPC——与微信模型同构，业务代码结构（`Page/App/Component`、生命周期名）也刻意保持近似。API 前缀 `my.*` vs `wx.*`、组件命名/属性差异是编译层抹平点。
2. **渲染栈**：主路线系统 WebView 混合渲染；未公开自研 GPU 渲染引擎下放小程序线的证据（*UNCERTAIN*：蚂蚁内部自绘资产是否服务小程序线）。小程序 canvas 场景由适配层补足——antvis/F2 799★（pushed 2026-05 仍活跃）是小程序侧 canvas 图表的主流解，其 Graphic 动画引擎对标 H5 端 ECharts 的精简路线。
3. **开放能力矩阵**：支付（my.tradePay）、会员/信用（芝麻）、卡券、位置/出行、IoT、小程序插件互跳——容器 API 面向"商业服务闭环"，与微信的"内容传播"取向形成系统性 API 差异；这套差异正是 OmniLet 统一 API 抽象层必须吸收的"商业能力半区"。
4. **语法规范输出**：2018-11 支付宝联合多家厂商成立小程序开放联盟，将支付宝语法作联盟基准——**吃透支付宝端语义≈拿到联盟端（百度/字节/360 等）的语义大盘**。
5. **多端输出历史**：官方未做编译期多端产品；跨端输出主要靠外部框架（Remax/Taro/uni-app 均支持编译到支付宝端），外部框架停滞即该端工具链真空。

## ③ 功能与特性

- **发布体系**：支付宝开放平台审核 + 灰度（按用户/设备百分比）+ 体验版/正式版；同样**不可嵌入自有 App**（联盟宿主间存在互投能力，但受商业关系支配）。
- **沙箱与权限**：容器级沙箱（域名白名单、登录态隔离、敏感 API 授权弹窗）——业务开发者不可触碰配置。
- **插件机制**：小程序插件（第三方开发者封装组件+页面供宿主小程序引用）——平台内复用粒度的先例。
- **开发者工具**：小程序开发者工具（IDE）闭源；类型定义与 UI 库开源但维护乏力（见 ①）。
- **生态位**：生活服务/金融/政务小程序密度最高，社交/内容类弱；线下场景（扫码进入）为主入口。

## ④ 优缺点

**优点**：双线程模型同源（微信经验与工具链认知可直接迁移）；支付/信用/卡券开放能力是差异化 API 富矿；联盟标准输出方（一次适配覆盖联盟族）；F2 等数据可视化配套仍活跃；线下扫码入口成熟。

**缺点/短板**：官方开源工具链维护断层（mini-types 冻结、mini-antui 停维）；第三方框架层（Remax/Antmove）双双停滞——端生态收缩证据链完整；流量分发弱于微信；作为编译目标的优先级低于微信但高于其他联盟端（白皮书 §8 路线图第二阶段单列）。

## ⑤ 对 OmniLet 的可借鉴点（映射到模块）

1. **编译目标第二位**：白皮书 §8 路线图第二阶段（6-12 个月）落地支付宝端——条件编译差异面 = `my.*` API 前缀映射表 + AXML/组件名差异表 + 生命周期/回调形状差异表（→ 编译引擎/平台差异注入；对应 architecture.md 不变量②"平台适配层是唯一平台 API 入口"，支付宝差异表与微信差异表并列于适配层，业务 IR 零平台分支）。
2. **开放能力 API 设计清单**：支付/登录/信用类 API 的参数与回调形状，是 OmniLet 统一 API 抽象层必须覆盖的"商业能力"半区；my.tradePay 的「签名订单 → 收银台 → 回调」三段式是支付 API 抽象的现成模板（→ 容器 SDK 原生桥）。按 architecture.md 不变量③，支付/信用这类端特有能力作统一 API 的**可选扩展能力集**——渲染后端行为一致，能力缺失时在适配层报错，业务侧只见统一 API。
3. **联盟语义收敛**：编译引擎按"联盟族"做差异收敛比逐端适配省一半——支付宝差异表 + 联盟端微调，即可覆盖百度/字节/360 语义大盘（→ 编译引擎/条件编译）。
4. **插件机制**：平台内组件/页面复用粒度先例——OmniLet 组件市场（白皮书 §8 三阶段）的颗粒度参照（→ 编译引擎/组件库，远期）。
5. **F2 的 canvas 图表路线**：小程序侧数据可视化的成熟解——OmniLet 标准模式图表能力的对标物；自研 GPU 引擎落地后成为其降级路径（→ 渲染引擎）。
6. **工具链维护断层是反面教材**：官方类型/UI 库冻结 → 生态依赖第三方 → 第三方停滞 → 端生态收缩。OmniLet 的 api-typings/组件库必须与 DSL 版本同仓同版本化发布（→ 编译引擎/测试）。

## ⑥ 不借鉴/规避点

1. **工具链开源面收缩的结构**：官方半心半意 + 第三方断层 = 开发者流失。OmniLet 设计器/工具链是产品主体，不能重蹈"配套工具二等公民"（→ 产品定位）。
2. **联盟互操作的不确定性**：联盟互投能力受商业关系支配（成员进出频繁），不可作为 OmniLet 发布策略的依赖前提；联盟语义收敛可用于编译层，不可用于运营承诺（→ 发布策略）。
3. **沙箱配置黑箱**：平台级沙箱不可定制是 FinClip/OmniLet 企业客户的共同痛点——OmniLet 沙箱权限模型（architecture.md ③ 遗留裁决：声明式清单 vs 运行时询问）正是差异化空间，勿学黑箱（→ 沙箱）。
